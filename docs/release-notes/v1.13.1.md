# v1.13.1

## 🐛 修复：后台写操作报 `CSRF token mismatch`（渠道/货源「测试连通」、新增/编辑/删除等）

**现象**：升级到 v1.12.85+（尤其 v1.12.90 之后）后，管理后台在「货源管理」点「测试连通」
（或任何写操作：新增/编辑/删除/同步/保存配置等）一律返回
`419 {"message":"CSRF token mismatch"}`。

**根因**：两个安全改动叠加所致：

1. **v1.12.85（安全审计 M3）**：后台登录态从「token 存 localStorage」改为「token 只存内存，
   刷新后用 HttpOnly 会话 Cookie 恢复登录」。因此**页面刷新后内存 Bearer token 丢失**，
   后续请求不再携带 `Authorization` 头，改走 Sanctum 会话 Cookie 认证。
2. **v1.12.90（安全审计 H-7）**：新增 `VerifyCsrfForSessionAuth` 中间件，对「会话认证的写请求」
   强制校验 CSRF token。

于是：更新完成后页面自动刷新 → token 丢失 → 会话认证的写请求缺少 CSRF token → 被守卫拦截。
顾客前台 `storefront/src/api/request.ts` 早已在写请求前 `fetch('/sanctum/csrf-cookie')` 并让
axios 自动携带 `X-XSRF-TOKEN` 头，而管理后台 `sysadmin/src/utils/http/index.ts` 一直缺少同样的
处理，因此只有后台中招。

**修复**：后台 HTTP 客户端与前台同口径——非只读请求（POST/PUT/DELETE）在缺少 `XSRF-TOKEN`
Cookie 时先请求 `/sanctum/csrf-cookie`，之后 axios 自动带 `X-XSRF-TOKEN` 头，同时满足
Sanctum stateful 的 `PreventRequestForgery` 与 `VerifyCsrfForSessionAuth` 两道 CSRF 校验。

**影响范围**：仅 `sysadmin` 前端（`src/utils/http/index.ts`）+ 重新编译的 `public/admin` 产物；
后端无改动、无数据库迁移、无依赖变更。

## 升级与使用

- 通过后台「在线更新」或 `git pull` 升级；刷新 `/admin` 即可（`NoCacheHtml` 已禁缓存
  index.html，正常会加载到新 hash 的 JS）。
- **部署提示**：`VerifyCsrfForSessionAuth` / Sanctum 判定「是否第一方前端」依赖
  `SANCTUM_STATEFUL_DOMAINS`（默认取 `APP_URL` 域名）。建议确认 `.env` 的 `APP_URL` 已设置为
  实际访问域名；若后台与 API 不同源，显式配置 `SANCTUM_STATEFUL_DOMAINS`。即便未配置，
  本修复也能让写请求携带 CSRF token 通过校验，但正确配置域名可避免其他依赖 stateful 判断的
  行为异常。
