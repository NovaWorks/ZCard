# v1.13.2

## 🐛 修复：后台同源写请求仍报 `419 CSRF token mismatch`（真正根因）

**现象**：v1.13.1 已让后台前端写请求自动携带 `X-XSRF-TOKEN`，但线上仍有接口
（如 `POST /api/admin/supply-sources/sync-queue-probe`、货源「测试连通」等）持续返回
`419 {"message":"CSRF token mismatch"}`。

**根因**：v1.12.90 引入的 `VerifyCsrfForSessionAuth` 中间件，把「是否第一方同源」的判断
**完全押在 `SANCTUM_STATEFUL_DOMAINS`（默认取 `APP_URL`）配置上**。当线上 `APP_URL` /
`SANCTUM_STATEFUL_DOMAINS` 没有包含真实访问域名（`kmigo.com` 这类生产域名）时，浏览器
明明是**同源请求**（请求头 `Sec-Fetch-Site: same-origin`），也会被误判成「跨站」，从而强制
要求 CSRF token；而 XSRF-TOKEN cookie 与当前会话 `_token` 又可能因登录/重建会话而失配，
于是即使带了 token 也过不去。

Laravel 自带的 `PreventRequestForgery` 早就处理了这一点：它把浏览器控制的
`Sec-Fetch-Site: same-origin` 作为「同源」的可靠信号直接放行（跨站攻击者的请求只会是
`cross-site`/`same-site`，无法伪造为 `same-origin`）。本修复让 `VerifyCsrfForSessionAuth`
与之同口径。

**修复**：

1. `app/Http/Middleware/VerifyCsrfForSessionAuth.php`：新增 `isSameOriginRequest()`——
   写请求若带 `Sec-Fetch-Site: same-origin`，视为第一方同源，跳过 CSRF 校验；
   仍保留 `SANCTUM_STATEFUL_DOMAINS` 判断以支持「第一方跨源 SPA」，也仍保留 CSRF token
   校验兜底（跨站 + 无 token 依然 419）。
2. 新增回归测试 `test_same_origin_session_write_skips_csrf_check`（同源会话认证写请求
   无 CSRF token 也应放行）。

**影响范围**：仅 `VerifyCsrfForSessionAuth` 中间件 + 1 个测试；无数据库迁移、无依赖变更、
无前端改动（v1.13.1 的前端 X-XSRF-TOKEN 逻辑保持不变，作为跨源场景的兜底）。

## 升级与使用

- 通过后台「在线更新」或 `git pull` 升级即可，**无需重新构建前端**。
- 仍建议把 `.env` 的 `APP_URL` 设为真实访问域名（或显式配置 `SANCTUM_STATEFUL_DOMAINS`），
  这能保证 Sanctum stateful 认证、回调地址生成等其他依赖也正确。
