## 环境要求速览

| 组件 | 版本要求 | 说明 |
|---|---|---|
| **PHP** | **8.3 或 8.4** | Laravel 13 要求,见下方扩展清单 |
| **MySQL** | **>= 8.0**(推荐 8.4) | utf8mb4 字符集 |
| **Redis** | **>= 6.0**(可选) | 不装可降级为 database 缓存 |
| **Composer** | **>= 2.8**(推荐最新 2.10.x) | **Laravel 13.8+ 要求 `composer-runtime-api ^2.2`,旧版会报错** |

### PHP 必需 / 推荐扩展

| 扩展 | 级别 | 用途 |
|---|---|---|
| `pdo_mysql` | **必需** | 数据库 |
| `mbstring` | **必需** | 多字节字符串(多语言) |
| `openssl` | **必需** | 加密 / HTTPS |
| `ctype` `tokenizer` `xml` `dom` `filter` `hash` | **必需** | Laravel 核心 |
| `curl` | **必需** | Stripe / 支付回调 / HTTP 请求 |
| `fileinfo` | **必需** | 文件上传 / MIME 检测 **(宝塔常缺,见问题 3)** |
| `bcmath` | **必需** | **金额精确计算(项目以「分」整数记账,缺了会出精度问题)** |
| `gd` 或 `imagick` | **必需** | 图片处理 / 图形验证码(`mews/captcha`) |
| `zip` | 推荐 | 压缩 / 导出 |
| `redis` | 可选 | 缓存加速 |

### 宝塔禁用函数(必须放行)

宝塔默认会禁用一批函数,其中以下函数 ZCard 必须可用,否则 **Composer 装不上** 或 **应用运行时崩溃**:

| 函数 | 为什么需要 |
|---|---|
| `putenv` | **必需** — Composer xdebug-handler、Laravel Dotenv(读 `.env`)都依赖它 **(见问题 4)** |
| `proc_open` | 推荐 — 队列进程 / `artisan` 子进程调用 |
| `passthru` `shell_exec` `exec` `system` | 视在线更新 / 命令调度需要放行 |

> 在宝塔面板 **「PHP 设置 → 禁用函数」** 中,把这些函数从列表里删除即可。

## 第 1 步:环境准备(关键)

> 以下以 **宝塔面板 + PHP 8.4** 为例。其他环境思路相同(改 php.ini / 用对应扩展安装方式)。
> 路径中的 `/www/server/php/84/` 是宝塔 PHP 8.4 的默认安装位置,若用 PHP 8.3 请改为 `/www/server/php/83/`。

### 1.1 确认 PHP 版本与扩展

```bash
# PHP 版本应为 8.3 或 8.4
/www/server/php/84/bin/php -v

# 列出已装扩展(逐一核对上面清单)
/www/server/php/84/bin/php -m
```

**缺扩展时,在宝塔面板安装:**

1. 软件商店 → 找到 **PHP-8.4** → 点「设置」
2. 选「安装扩展」标签
3. 找到缺失的扩展(尤其 **fileinfo、bcmath、gd、zip**)→ 点「安装」
4. 等待编译完成(约 1–2 分钟 / 个)

### 1.2 放行被禁用的函数

1. 宝塔面板 → **PHP-8.4 → 设置 → 禁用函数**
2. 在列表中找到并 **删除**:`putenv`(必须)、`proc_open`(推荐)
3. 保存

**或命令行改 ini**(php.ini 与 php-cli.ini 两个文件都要改):

```bash
# 查看当前禁用列表
grep -i "disable_functions" /www/server/php/84/etc/php.ini
grep -i "disable_functions" /www/server/php/84/etc/php-cli.ini

# 移除 putenv / proc_open
sed -i 's/, *putenv//; s/putenv, *//; s/putenv//; s/, *proc_open//; s/proc_open, *//; s/proc_open//' \
    /www/server/php/84/etc/php.ini /www/server/php/84/etc/php-cli.ini

# 重载 PHP-FPM
/etc/init.d/php-fpm-84 reload 2>/dev/null || systemctl reload php-fpm-84 2>/dev/null
```

验证:

```bash
/www/server/php/84/bin/php -r "var_dump(function_exists('putenv'));"   # 应输出 bool(true)
```

### 1.3 升级 Composer 到最新版

Laravel 13.8+ 要求 `composer-runtime-api ^2.2`(即 Composer ≥ 2.8)。宝塔自带或系统 `composer` 可能是 2.0/2.1 老版本,**必须升级**,否则会在 `composer update/install` 时报满屏 Deprecated 警告并最终解析失败。

```bash
# 用项目对应的 PHP 下载最新 composer.phar
cd /tmp
/www/server/php/84/bin/php -r "copy('https://getcomposer.org/installer', 'composer-setup.php');"
/www/server/php/84/bin/php composer-setup.php
/www/server/php/84/bin/php -r "unlink('composer-setup.php');"

# 安装到统一位置
mv composer.phar /usr/local/bin/composer
chmod +x /usr/local/bin/composer

# 验证:应显示 2.8.x 及以上、runtime-api 2.2
/www/server/php/84/bin/php /usr/local/bin/composer --version
```

> 💡 **建议**做软链,让 `php` / `composer` 命令默认指向正确版本,避免后续 `artisan` 命令用到错误的 PHP:
>
> ```bash
> ln -sf /www/server/php/84/bin/php /usr/local/bin/php
> ```

## 第 2 步:安装依赖

进入项目目录,使用 **`install`**(严格按锁文件 `composer.lock` 安装),**不要用 `update`**。

```bash
cd <你的项目目录>

# 确认锁文件已部署到服务器(很关键)
ls -la composer.lock    # 应存在,大小约 400KB+

# 生产环境安装:去掉 dev 依赖 + 优化自动加载
/www/server/php/84/bin/php /usr/local/bin/composer install --no-dev --optimize-autoloader
```

> ⚠️ **为什么必须用 `install` 而不是 `update`?**
> - `install` 严格按 `composer.lock` 安装,版本与开发者测试一致;
> - `update` 会重新解析所有包版本,可能拉到不兼容的新版本,线上容易出问题;
> - 若服务器没有 `composer.lock`,`install` 会退化成 `update` 行为 —— 所以务必确认锁文件随代码一起部署。

---

## 第 3 步:完成安装

依赖装好后,按 [README](../README.md) 的「安装方式」二选一:

```bash
# 命令行安装(运维人员)
cp .env.example .env
php artisan key:generate
php artisan zcard:install            # 交互式:提示输入数据库 + 管理员
# 或跳过数据库交互:
php artisan zcard:install --skip-db --email=admin@example.com --password=yourpassword
```

或浏览器访问 `http://你的域名/install` 走 Web 安装向导。

安装完成后:

```bash
# 修正 vendor 属主(宝塔 PHP-FPM 用户通常为 www)
chown -R www:www vendor bootstrap/cache storage

# 访问验证
# http://你的域名/        → 前台商城
# http://你的域名/admin/   → 后台管理
```

## 常见问题排查(FAQ)

### 问题 1:Composer 满屏 Deprecated 警告 + `composer-runtime-api` 不匹配

**现象**

执行 `composer update` / `install` 时:

- 满屏 `Implicitly marking parameter $xxx as nullable is deprecated`
- 最后报错:
  ```
  laravel/framework[v13.8.0...] require composer-runtime-api ^2.2
  -> found composer-runtime-api[2.0.0] but it does not match the constraint.
  ```

**原因**

服务器上的 Composer 太旧(2.0 / 2.1 时代),其代码在 PHP 8.3/8.4 下触发大量 deprecation;且不提供 Laravel 13.8+ 要求的 `composer-runtime-api 2.2`。

**解决**

升级 Composer 到最新版,见 [1.3 升级 Composer](#13-升级-composer-到最新版)。

---

### 问题 2:首页报 `Failed to open stream: vendor/autoload.php`

**现象**

访问首页报:

```
Warning: require(.../public/../vendor/autoload.php): Failed to open stream:
No such file or directory in .../public/index.php on line 14
```

**原因**

`vendor/` 目录不存在 —— 依赖根本没装成功。这通常是 [问题 1](#问题-1composer-满屏-deprecated-警告--composer-runtime-api-不匹配) / [问题 3](#问题-3ext-fileinfo-is-missing-from-your-system) / [问题 4](#问题-4call-to-undefined-function-putenv) 任一导致 `composer install` 中断后的**表象**,不是独立 bug。

**解决**

先按其它问题让 `composer install` 成功跑完,`vendor/autoload.php` 自然生成。验证:

```bash
ls -la vendor/autoload.php    # 应存在
```

### 问题 3:`ext-fileinfo is missing from your system`

**现象**

`composer install` 时报:

```
league/flysystem-local 3.31.0 requires ext-fileinfo * -> it is missing from your system.
To enable extensions, verify that they are enabled in your .ini files:
    - /www/server/php/84/etc/php-cli.ini
```

**原因**

PHP 缺少 `fileinfo` 扩展。宝塔部分精简安装默认不带它。

**解决**(推荐真正装上,不要跳过)

在宝塔面板安装:

1. 软件商店 → **PHP-8.4 → 设置 → 安装扩展**
2. 找到 **fileinfo** → 安装

装完验证:

```bash
/www/server/php/84/bin/php -m | grep fileinfo    # 应输出 fileinfo
```

然后重新 `composer install`。

> 🚫 **不要**长期用 `--ignore-platform-req=ext-fileinfo` 绕过 —— 它只跳过依赖检查,**应用运行时一旦用到文件上传 / MIME 检测(商品图、头像等)就会报错**。

### 问题 4:`Call to undefined function putenv()`

**现象**

执行 `composer install` 直接崩:

```
PHP Fatal error: Uncaught Error: Call to undefined function
Composer\XdebugHandler\putenv() in .../xdebug-handler/src/Process.php:98
```

或一个隐蔽表现:**用 `/www/server/php/84/bin/php composer --version` 能跑,直接敲 `composer` 却崩** —— 因为两者加载的 `php.ini` 不同,直接敲时被 `disable_functions` 拦截。

**原因**

`putenv` 被宝塔加入 `disable_functions`。这不只影响 Composer —— **Laravel 读 `.env`(Dotenv)、队列进程都依赖它**,不放开会导致应用读不到环境变量。

**解决**

从禁用函数列表移除 `putenv`,见 [1.2 放行被禁用的函数](#12-放行被禁用的函数)。

### 问题 5:访问首页 500 / 白屏(storage 目录不可写)

**现象**

`composer install` 和 `git pull` 都成功,但访问首页 **500** 或白屏,日志里看不到清晰错误(或 Ignition 报各种框架内部错误)。

**原因**

`composer install` / `git pull` 用 **root** 执行,新生成的 `storage/`、`bootstrap/cache/` 目录属主是 root。而宝塔的 PHP-FPM 以 **www** 用户运行 → 这些目录**读得到但写不了** → Laravel 写 session / 日志 / 编译视图时崩溃 → 500。

这是**最常见的部署后 500 根因**,且非常隐蔽(CLI 命令以 root 跑都正常,只有 Web 请求才崩)。

**解决**

```bash
cd <你的项目目录>

# 把整个项目关键目录属主改回 www(宝塔 PHP-FPM 用户)
chown -R www:www storage bootstrap/cache vendor

# 确保目录可写
chmod -R 775 storage bootstrap/cache

# 重启 PHP-FPM(清 opcache)
/etc/init.d/php-fpm-84 restart
```

> 💡 **验证**:
> ```bash
> sudo -u www test -w <项目目录>/storage && echo "✅ www 可写" || echo "❌ 不可写"
> ```
> 从 v1.1.5 起,Web 安装向导和 `zcard:install` 命令会**自动尝试 chmod 修复**关键目录;但属主(chown)仍需手动执行(因为 PHP-FPM 进程无 chown 权限)。

### 问题 6:`tempnam(): file created in the system's temporary directory`

**现象**

访问首页 500,Ignition 错误页标题是 `tempnam(): file created in the system's temporary directory`。

**原因**

宝塔站点级 `.user.ini` 设置了 `open_basedir` 限制,把 PHP 能访问的路径锁在网站目录 + `/tmp`。当框架需要写的临时目录**不在允许列表**时触发此警告。

**排查**

```bash
# 查看 .user.ini(open_basedir 在这里设,不在 php.ini)
cat <项目父目录>/.user.ini

# 典型内容(注意路径层级):
# open_basedir=<项目父目录>/:/tmp/    ← 正确(包含 ZCard 父目录)
```

**解决**

确保 `open_basedir` 包含项目根目录和 `/tmp/`。在宝塔面板:**网站 → 你的站点 → 设置 → 配置修改**,把 `open_basedir` 改为:

```
open_basedir=/www/wwwroot/你的域名/:/tmp/
```

> ⚠️ 路径要用**项目父目录**,不要用项目目录本身,否则 Laravel 访问 `/tmp` 等系统路径会被拦。
>
> 如果排查后仍不确定,可临时**关闭防跨站攻击**(宝塔面板「网站设置 → 防跨站攻击 open_basedir」开关),验证是否为此问题。

### 问题 7:`Module "mbstring" is already loaded`

**现象**

每次执行 PHP 命令都报 `PHP Warning: Module "mbstring" is already loaded in Unknown on line 0`。

**原因**

`mbstring` 扩展被加载了两次:既编译进 PHP,又在 `php.ini` 里写了 `extension=mbstring`。

**解决**

```bash
# 找到重复的 extension 行(php.ini 和 php-cli.ini 都查)
grep -rn "extension.*mbstring" /www/server/php/84/etc/php.ini /www/server/php/84/etc/php-cli.ini

# 删除重复的那一行(保留一个,或都删掉如果已编译进 PHP)
# 例如:
sed -i '/extension=mbstring/d' /www/server/php/84/etc/php.ini
sed -i '/extension=mbstring/d' /www/server/php/84/etc/php-cli.ini

# 重启 PHP-FPM
/etc/init.d/php-fpm-84 restart
```

> 这只是 Warning,不影响功能,但建议清理避免日志噪音。

### 问题 8:货源接口报 404(`supply-sources/{id}/products/preview` could not be found)

**现象**

- 后台「货源对接 → 商品预览 / 勾选导入」无法使用
- 直接请求 `GET /api/admin/supply-sources/3/products/preview` 返回 404
- 报错可能是 Laravel JSON:`The route api/admin/supply-sources/3/products/preview could not be found`
  (也可能被 nginx 换成了 HTML 404 页面,见问题 9)

**原因**(按可能性排序)

1. **线上代码版本 < v1.9.2**:`products/preview`、`products/import` 路由是 **v1.9.2** 加入的,
   `products/debug` 是 **v1.9.5** 加入的。代码旧 → 路由不存在 → 404。
2. **git pull 未成功 / 工作区混乱**:手动 `git pull` 时本地有未提交改动(常见是
   `sysadmin/src/locales/langs/zh.json` 等被改过)导致 **Abort**,代码停留在旧版。
3. **PHP-FPM OPcache 缓存旧代码**:代码更新后未重启 PHP-FPM,`routes/api.php` 仍执行旧的
   字节码(此时 `route:clear` 无效,因为清的是 Laravel 缓存不是 PHP 字节码缓存)。
4. **货源 id 不存在**:`supply-sources/{id}` 的 id 在数据库中没有记录。
   (v1.9.6+ 已优化:会返回带「可用货源 id」列表的友好 JSON,便于定位)

**解决**(按顺序)

```bash
cd <你的项目目录>

# ① 确认版本与路由是否在源码里
cat VERSION                                 # 应 ≥ 1.9.2
grep -n "products/preview" routes/api.php   # 应能搜到,搜不到 = 代码旧

# ② 代码旧 → 强制同步到 GitHub 最新(⚠️ 会丢弃本地未提交改动)
git fetch origin main
git stash                                   # 想保留本地改动就先备份(可选)
git reset --hard origin/main
git stash pop                               # 恢复本地改动,可能有冲突(可选)

# ③ 清缓存 + 重启 PHP-FPM(清 OPcache,关键!)
php artisan route:clear && php artisan config:clear
/etc/init.d/php-fpm-84 restart

# ④ 验证路由已注册
php artisan route:list --path=supply-sources

# ⑤ 确认货源 id 存在(不是 404 的另一原因)
php artisan tinker --execute='print_r(App\Models\SupplySource::all(["id","name"])->toArray())'
```

**预防**

- **优先用后台「在线更新」按钮**,它会自动 `git pull` + 清缓存 + 迁移 + 重建前端,不会踩手动更新
  的坑;**不建议手动 `git pull`**。
- 手动 pull 前先 `git status` 检查本地改动,有改动先 `git stash`。
- 更新代码后**必须** `php artisan route:clear && php artisan config:clear` 并**重启 PHP-FPM**
  (否则 OPcache 可能继续跑旧代码,路由不生效)。

### 问题 9:接口报错返回 HTML 404 页面而不是 JSON(`error_page 404 /404.html` 掩盖错误)

**现象**

- 调用 `/api/...` 接口报错时,返回的是 nginx 风格的 HTML 404 页面
  (页面标题 `404 Not Found`、带 `<center>nginx</center>` 或站点 `/404.html` 内容),
  而不是 JSON,导致无法判断是「路由不存在 / 资源不存在 / 权限不足」等真实原因。
- 典型场景:货源接口 404、后台列表接口 404,看到的全是同一个 HTML 页面。

**原因**

宝塔新建站点的默认配置里有一行:

```nginx
error_page 404 /404.html;
```

当 Laravel 返回 **404 状态码**(路由不存在、模型不存在等,响应体是 JSON)时,
nginx 会用 `/404.html` 的 **HTML 内容替换掉 JSON 响应体**。API-First 系统的
404 JSON(包括 v1.9.6 加的「货源不存在 + 可用 id」友好提示)全都会被吞掉。

**解决**

宝塔面板 → 网站 → 你的域名 → 设置 → **配置文件**,注释掉该行:

```nginx
#error_page 404 /404.html;
```

或让 API 路径保持 JSON、仅前端页面走错误页:

```nginx
location ~ ^/api/ {
    error_page 404 = @api404;
}
location @api404 {
    return 404;
}
```

改完:

```bash
nginx -t && nginx -s reload
```

> 该配置属于部署环境默认值,不是 ZCard 代码问题;注释掉后 API 的 JSON 错误就能正常透传,
> 排查问题会容易很多。

### 问题 10:上传的图片 / `/storage/...` 访问 403「访问被拒绝」,图片不显示

**现象**

- 素材管理 / 商品图上传成功后,图片 URL(`https://域名/storage/media/2026/08/xxx.png`)访问返回 **403 或 404**
- 页面显示「访问被拒绝」,图片裂图 / 无法预览
- 但后台列表能看到图片记录、能删除(文件其实已写入磁盘)

**原因**

素材图片存储在 `storage/app/public/media/`,必须通过 **`public/storage` 软链接**才能经 `/storage/...` 访问
(这是 Laravel 标准 `php artisan storage:link` 创建的结构)。若该软链接缺失或指向错误:

- 图片请求不会命中 nginx 的静态文件服务,而是被转发到 Laravel(走 `index.php`)
- Laravel 对 `/storage/` 没有对应路由 → 返回 **403「访问被拒绝」**(或 404)

> 排查关键:对比 `/admin/index.html`、`/storefront/index.html` 是否 200 正常、唯独 `/storage/...` 403。
> 若 `admin` / `storefront` 正常而 `storage` 异常,几乎可以断定是软链接问题。

**解决**

```bash
cd <你的项目目录>

# ① 检查软链接是否存在及指向
ls -la public/storage
# 期望:public/storage -> ../storage/app/public

# ② 不存在或指向错误 → 重建(Laravel 官方命令)
rm -f public/storage
php artisan storage:link

# ③ 验证图片可访问
curl -I https://你的域名/storage/media/2026/08/某图片.png   # 期望 HTTP/2 200
```

Docker 环境(如 Laravel Sail / 宝塔 Docker):

```bash
docker exec -it <你的容器名> bash
cd /www/sites/zcard/index        # 容器内项目路径
php artisan storage:link
```

**预防**

- v1.11.11 起,**安装流程会自动创建该软链接**(`InstallCommand` 与 Web 安装向导均已在迁移后执行 `storage:link`)。
- 升级旧版本站点后,请手动执行一次 `php artisan storage:link`。
- `public/storage` 是运行时产物(已被 .gitignore 忽略),**不会随 git 同步**,每台服务器都要单独创建。

### 问题 11:`composer install` 报 `Your lock file does not contain a compatible set of packages` / `symfony/yaml requires php >=8.4.1`

**现象**

- 服务器 `composer install` 报错,要求先 `composer update`
- 常见报错如:
  ```
  Problem: symfony/yaml v8.1.2 requires php >=8.4.1 -> your php version (8.3.0) does not satisfy that requirement.
  Problem: yansongda/pay v3.7.20 requires ext-bcmath * -> it is missing from your system.
  ```

**原因(分两类)**

1. **服务器 composer.lock 是旧版**:代码更新后(`git pull` / 在线更新),服务器上的 `composer.lock`
   没同步(可能是 git 冲突、或手动 pull 未成功),旧的 lock 里锁定了要求 PHP 8.4 的
   `symfony/* v8.1.x` 依赖,而服务器是 PHP 8.3 → 依赖校验失败。
2. **缺 `ext-bcmath` 扩展**:`yansongda/pay`(易支付等支付通道)、`dragon-code/support` 强制要求
   `bcmath` 扩展,服务器 PHP 未安装 → composer 校验失败。

**解决(按顺序)**

```bash
cd <你的项目目录>

# ① 先确认代码/ lock 已同步到最新(重要!)
git status
git log --oneline -1                  # 应 ≥ v1.11.3 的提交(该版本已将 Symfony 锁定到 7.4,兼容 PHP 8.3)
grep -A1 '"name": "symfony/yaml"' composer.lock | grep version   # 应为 v7.4.x,而不是 v8.x

# ② lock 旧 → 强制同步
git fetch origin main
git reset --hard origin/main          # ⚠️ 会丢弃本地未提交改动,先 git stash 备份

# ③ 安装 bcmath 扩展
# 宝塔:软件商店 → PHP → 设置 → 安装扩展 → 勾选 bcmath → 安装
# Docker 官方镜像:Dockerfile 加 RUN docker-php-ext-install bcmath 后重建
#   (容器内应急:docker exec -it <容器> bash && docker-php-ext-install bcmath)

# ④ 重装依赖
rm -rf /tmp/.composer                 # 清掉 Composer 全局配置缓存(权限问题,见问题 12)
composer install

# ⑤ 验证
php artisan --version
```

**预防**

- **优先用后台「在线更新」按钮**,不要手动 `git pull`。
- v1.11.3 起 `composer.json` 已:
  - 将 17 个 `symfony/*` 组件锁定 `^7.4`(仅要求 PHP 8.2,最低 PHP 真正降到 8.3)
  - 设置 `config.platform.php: 8.3.0`,防止 `composer update` 把依赖拉回要求 PHP 8.4 的版本
- `bcmath` 是**服务器扩展**,必须在 PHP 环境层面安装,代码无法替代。

### 问题 12:`composer install` 报 `The file "/tmp/.composer/config.json" is not readable`

**现象**

服务器 `composer install` 报:
```
In JsonFile.php line 205:
The file "/tmp/.composer/config.json" is not readable.
```

**原因**

Composer 默认把全局配置写到 `$COMPOSER_HOME`(未设置时通常是 `/tmp/.composer` 或 `~/.composer`)。
该文件可能由其他用户(如 root)创建,运行用户(如 `www-data`)无读权限 → 报不可读。

**解决**

```bash
# 方式一:删除损坏的全局配置,让 Composer 重新生成
rm -rf /tmp/.composer
composer install

# 方式二:显式指定 COMPOSER_HOME 到项目内目录(最稳)
mkdir -p /www/sites/zcard/index/.composer
chown -R www-data:www-data /www/sites/zcard/index/.composer
export COMPOSER_HOME=/www/sites/zcard/index/.composer
composer install
```

**预防**

- v1.11.4 起 `composer.json` 已设置 `config.home` / `config.cache-dir` 指向项目根目录的 `.composer/`,
  Composer 会在项目内读写配置与缓存,绕开系统 `/tmp` 的权限冲突。升级后按上面方式重新 install 即可。
- `.composer/` 已加入 `.gitignore`,不会进仓库。

## 部署后检查清单

```bash
cd <你的项目目录>

# ⚠️ 最重要:权限属主(root 跑 composer/git pull 后必须执行,否则 Web 必 500)
chown -R www:www storage bootstrap/cache vendor
chmod -R 775 storage bootstrap/cache
# 验证 www 用户可写:
sudo -u www test -w storage && echo "✅ storage 可写" || echo "❌ 不可写"

# 1. PHP 版本与扩展
php -v                                           # 8.3 / 8.4
php -m | grep -iE 'fileinfo|bcmath|gd|pdo_mysql|curl|mbstring|openssl'

# 2. 禁用函数已放行
php -r "var_dump(function_exists('putenv'));"    # bool(true)

# 3. 依赖已装
ls vendor/autoload.php                           # 存在

# 4. 关键目录存在且可写
ls -d storage bootstrap/cache

# 5. 环境配置
test -f .env && echo ".env OK"
php artisan key:generate --check 2>/dev/null || php artisan key:generate

# 6. 数据库连接
php artisan migrate --force

# 7. storage 软链接(素材/上传图片经 /storage/ 访问必需,v1.11.11+ 安装自动建)
ls -la public/storage
# 期望:public/storage -> ../storage/app/public
# 缺失或指向错误时执行:php artisan storage:link

# 8. 缓存清一遍 + 重启 PHP-FPM
php artisan optimize:clear
/etc/init.d/php-fpm-84 restart
```

逐项通过后,访问 `http://你的域名/`(前台)和 `http://你的域名/admin/`(后台)即可。
再验证图片访问:`curl -I http://你的域名/storage/media/...` 应返回 200。

> **首次部署捷径**:clone + `composer install` 后,直接访问首页会自动跳转 `/install` 安装向导(v1.1.2+),按向导填写数据库和管理员信息即可完成安装。安装向导会自动处理目录权限和 APP_KEY 生成。
